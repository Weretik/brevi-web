# Готовність специфікації

- [ ] Мета, актор, межі та виключення визначені явно.
- [ ] Кожне бізнес-правило має стабільний `R-*`.
- [ ] Кожен приймальний сценарій має стабільний `SC-*` і структуру «За умови / Коли / Тоді».
- [ ] Сценарії не містять назв компонентів, хуків, сховищ, бібліотек або файлів.
- [ ] Фактичні застосунки, шляхи, цілі Nx, конфігурації та тестові файли перевірені.
- [ ] `design/frontend.md` містить початковий аудит наявного коду feature й заплановані межі відповідальності з точними шляхами.
- [ ] Зафіксовано architecture baseline: Nx projects/tags/constraints, потрібні domain layers, вкладеність, public entry points, approved state/data stack і test targets.
- [ ] Кожна виявлена розбіжність у dependency chain має ready `EN-*`/`TS-*` або dependency на remediation SDD; невиправлене порушення не приховане як «наявний pattern».
- [ ] Кожен сценарій має рівень тестування за ризиком і ціль для свідчень.
- [ ] Кожна `TS-*`/`EN-*` має одну відповідальність і всі обов'язкові поля.
- [ ] Кожна виконувана задача завершує розділ `Робота` обов'язковою перевіркою відповідальності змінених файлів, включно з критеріями розділення за архітектурними межами та винятком для невеликого цілісного файла.
- [ ] Трасування та залежності повні; блокери визначені явно.
- [ ] Для API feature: `contracts/api-contract.md` містить кожен `operationId`, backend OpenAPI source і commit/tag, snapshot provenance, клієнтські рішення й `EN-*` для відсутнього tooling. Для feature без API файл видалено.
