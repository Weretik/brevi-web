# SDD: поетапна реалізація Admin feature

> **Призначення:** використовуйте цей шаблон для feature, яку неможливо безпечно
> реалізувати одним невеликим change set. Спочатку створіть головну
> специфікацію, потім окремий Markdown-файл для кожної незалежно reviewable фази.
> Не створюйте фазу або папку, якщо відповідна відповідальність не потрібна.

## Як використовувати шаблон

1. Скопіюйте розділ «Головна специфікація» до
   `docs/specs/admin/<domain>/<feature>.md`.
2. Створіть файли фаз у `docs/specs/admin/<domain>/phases/` з префіксом порядку:
   `01-...md`, `02-...md`.
3. Кожна фаза має одну мету, чіткі межі, критерії приймання та власну перевірку.
4. Починайте наступну фазу лише після того, як попередня пройшла її перевірки
   або в документі явно зафіксовано причину, чому це неможливо.
5. Під час реалізації оновлюйте статус фази, результат, фактичні команди
   перевірки й ризики. Не переписуйте погоджені межі без запису в історії змін.

## Архітектурне рішення

Опишіть розподіл відповідальностей. Не додавайте шар, якщо в ньому немає
окремої відповідальності.

```text
libs/admin/<domain>/
├── model/        # domain entities, query, defaults, pure invariants
├── data-access/  # endpoint, DTO, mapper, RTK Query hooks
├── ui/           # reusable presentational components, forms, dialogs, якщо потрібні
└── feature/      # route, page orchestration, feature-only components/state
```

- `model` не залежить від React, HTTP або browser API.
- `data-access` залежить від `model`, але не містить JSX чи маршрутів.
- `ui` не виконує HTTP і не керує server state.
- `feature` збирає сторінку, hooks та route; не містить transport DTO.
- Усі міжбібліотечні імпорти йдуть через публічний `src/index.ts` alias.

### Форми, модалки та стан

- Повторно використовувана form, її поля, синхронна валідація props і
  presentational dialog розміщуються в `ui/forms` або `ui/components`. Вони
  отримують значення, помилки, `onSubmit`, `onCancel` і `open` через props; не
  викликають API, router або RTK Query hooks.
- Модалка, що належить лише одному користувацькому сценарію, розміщується в
  `feature/components`. Page або feature hook відкриває її, викликає mutation і
  передає в `ui` готові props та callbacks.
- Server state не дублюється в reducer: дані запитів, loading/error мутацій і
  cache належать RTK Query у `data-access`.
- Локальний стан сторінки (відкрита модалка, чернетка, вибрані рядки, активна
  вкладка) зберігається в компоненті або feature hook. Коли цей стан має кілька
  пов'язаних переходів, повинен переживати remount чи використовується кількома
  частинами feature, reducer/actions розміщуються в `feature/state` і явно
  експортуються для реєстрації в store.
- Не створюйте Redux reducer для одного простого `boolean` або стану, що існує
  лише в одному компоненті; використовуйте локальний `useState`.

## Типовий порядок реалізації

### Фаза 01 — доменна модель і контракт

- Зафіксувати API contract або адаптувати наявний.
- Створити domain entities, query, defaults, pure validation/normalization у
  `libs/admin/<domain>/model`.
- Не створювати Axios, RTK Query, JSX або route.

### Фаза 02 — data access

- Додати private DTO в `contracts/`.
- Додати mapper DTO ↔ domain model та validation на API boundary.
- Оголосити endpoint через `baseApi.injectEndpoints` і експортувати typed hook.
- Перевірити, що `data-access` не містить UI, router або feature state.

### Фаза 03 — reusable UI, якщо потрібний

- Створити presentational-компоненти, таблиці, форми або UI-стани в `ui`.
- Приймати дані, callbacks і стан через props.
- Не імпортувати `data-access`, RTK Query hook або router.

### Фаза 04 — feature, route і page

- Додати route entry, page composition, feature-only controls та локальний стан.
- Для feature-only модалки розмістити orchestration-компонент у
  `feature/components`; reusable dialog/form лишається в `ui`.
- Якщо потрібен reducer, створити `feature/state/<domain>.slice.ts`, описати
  його owner, початковий стан, actions та місце реєстрації в root store.
- Не копіювати в reducer RTK Query data, loading або API error state.
- Викликати exported data-access hook у feature, а не в `ui`.
- Передати готові domain-моделі та callbacks у presentational UI.

### Фаза 05 — інтеграція та приймання

- Перевірити повний користувацький сценарій, loading/empty/error стани,
  permissions і keyboard/a11y поведінку, якщо вони належать feature.
- Запустити релевантні lint, unit, integration/e2e та build.
- Зафіксувати фактичні команди, ручні кроки й залишкові ризики в головній
  специфікації та фазі 05.
