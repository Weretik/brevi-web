# SDD: поетапна міграція візуального шаблону Admin

## 1. Мета

Поступово замінити поточні чернеткові екрани `apps/admin` візуальною системою та компонуванням із [референсного шаблону](file:///D:/RiderProjects/template), зберігши фірмові кольори Kedr, наявну архітектуру React/MUI, маршрутизацію та контракти API.

Шаблон є візуальним та UX-референсом. Його код Next.js, демонстраційні дані, зображення, тексти Devias і зовнішні посилання не переносяться без окремої задачі.

## 2. Контекст

| Область     | Поточний стан                                | Роль у міграції                                                  |
| ----------- | -------------------------------------------- | ---------------------------------------------------------------- |
| Admin       | React 19, MUI 9, React Router, Nx            | Цільовий застосунок                                              |
| Тема Admin  | `apps/admin/src/app/theme/admin-theme.ts`    | Єдина точка налаштування MUI-токенів Admin                       |
| Каркас      | `libs/admin/core/shell/src/admin-layout.tsx` | Базове компонування всіх захищених сторінок                      |
| Авторизація | `libs/admin/core/auth/src/auth-session.ts`   | Використовується для виходу; UI не отримує облікові дані напряму |
| Шаблон      | `D:\RiderProjects\template`                  | Джерело структури, розмірів, станів і візуальних рішень          |

### Додаткові правила

- `apps/admin` є точкою композиції; доменний код розміщується в `libs/admin`.
- Shell належить `admin/core/shell`, а тема — `apps/admin/src/app/theme`.
- API та серверний стан залишаються в доменному `data-access` через RTK Query.
- Нові домени customers, orders і account реалізуються лише після окремих SDD-специфікацій і контрактів API.
- Документація та інтерфейс Admin ведуться українською мовою.
- Зміни відповідають `docs/architecture/admin/` і стандартам Admin.

## 3. Незмінні межі

- Фірмові кольори з `libs/shared/theme/src/lib/design-tokens.json` і значення кольорів `admin-theme.ts` не змінюються.
- `primary.main` залишається `#18b125`; семантичні кольори `info`, `success`, `warning`, `error` зберігають поточні значення та призначення.
- Не змінюються API-клієнт, `auth-session.ts`, Redux store, конфігурація середовища, глобальна маршрутизація storefront і Angular-застосунок.
- Не додаються залежності лише заради точного копіювання шаблону. Для іконок використовується вже встановлений `@mui/icons-material`.
- Дані, бренд, зображення та промоблоки шаблону не копіюються.
- Візуальна міграція не створює фіктивних бізнес-функцій: сторінки без затвердженого API повинні мати явно позначений статичний або порожній стан.

## 4. Цільова архітектура

### Бібліотеки та відповідальність

| Розташування                             | Відповідальність                                                             |
| ---------------------------------------- | ---------------------------------------------------------------------------- |
| `apps/admin/src/app/theme`               | Тема MUI, палітра, типографіка, тіні та перевизначення компонентів           |
| `libs/admin/core/shell`                  | Компонування, навігація desktop/mobile, верхня панель, профіль і breadcrumbs |
| `libs/admin/dashboard/feature`           | Екран dashboard і його композиція                                            |
| Новий домен Admin за появи бізнес-логіки | Сторінки customers, orders, account за правилами `docs/architecture/admin/`  |
| `libs/admin/*/ui`                        | Повторно використовувані суто доменні візуальні компоненти                   |

Не створювати спільний UI-kit до появи щонайменше двох підтверджених споживачів. Першу реалізацію кожного елемента тримати поруч із доменом; виділяти в `ui` лише за реального повторного використання.

### Навігація та маршрути

Цільові сторінки Admin:

| Сторінка               | Маршрут      | Призначення                           | Дані та статус                                               |
| ---------------------- | ------------ | ------------------------------------- | ------------------------------------------------------------ |
| Вхід до системи        | `/login`     | Автентифікація менеджера              | Потребує чинного auth-контракту                              |
| Реєстрація             | `/register`  | Створення облікового запису менеджера | Потребує окремого auth-контракту та правил доступу           |
| Dashboard              | `/dashboard` | Огляд робочого простору               | Реальні метрики або інформативний порожній стан              |
| Товари                 | `/products`  | Керування каталогом товарів           | Використовує наявний домен products                          |
| Клієнти                | `/customers` | Перегляд і керування клієнтами        | Реалізується після погодження контракту API                  |
| Замовлення             | `/orders`    | Перегляд і керування замовленнями     | Реалізується після погодження контракту API                  |
| Налаштування менеджера | `/account`   | Ім'я та телефон поточного менеджера   | Дані лише з контракту session/profile; без прямого HTTP у UI |

Цільові шляхи, якщо відповідну функціональність реалізовано:

| Шлях                                              | Призначення            | Статус на першому етапі                      |
| ------------------------------------------------- | ---------------------- | -------------------------------------------- |
| `/`                                               | Перехід на dashboard   | Перенаправляє на `/dashboard`                |
| `/login`                                          | Вхід до системи        | Публічний маршрут після погодження auth      |
| `/register`                                       | Реєстрація             | Публічний маршрут після погодження auth      |
| `/dashboard`                                      | Dashboard              | Замінити поточний чернетковий екран          |
| `/products` або погоджений поточний шлях каталогу | Товари/каталог         | Зберегти наявну публічну URL-адресу          |
| `/customers`                                      | Клієнти                | Новий маршрут лише разом із функціональністю |
| `/orders`                                         | Замовлення             | Новий маршрут лише разом із функціональністю |
| `/account`                                        | Налаштування менеджера | Новий маршрут разом із контрактом профілю    |

Для сторінки `/account` мінімальний затверджений профіль містить ім'я та номер телефону поточного менеджера. Поля відображаються й змінюються лише через окремий контракт session/profile; токени, паролі та прямі HTTP-виклики з UI заборонені.

`AdminLayout` залишається батьківським елементом маршруту з `Outlet`. Активність пункту меню визначається через `useLocation`, а переходи виконуються `Link` із `react-router-dom`; API Next.js (`next/link`, `usePathname`, `useRouter`) не використовується.

## 5. Візуальні вимоги

### 5.1 Тема MUI

В `admin-theme.ts` поетапно перенести із шаблону:

- точки переходу: `xs 0`, `sm 600`, `md 900`, `lg 1200`, `xl 1440`;
- типографічну шкалу й вагу, адаптувавши лише до поточного сімейства `Inter, "Segoe UI", Roboto, Helvetica, Arial, sans-serif`;
- масив `shadows` як правила висоти;
- `shape.borderRadius: 8` і локальні радіуси компонентів із перевизначень;
- перевизначення для `MuiAvatar`, `MuiButton`, `MuiCard`, `MuiCardHeader`, `MuiCardContent`, `MuiLink`, `MuiStack`, `MuiTab`, `MuiTableBody`, `MuiTableCell`, `MuiTableHead` лише після перевірки застосовності.

Значення палітри із шаблону (`neonBlue`, нейтральні кольори Devias тощо) не переносяться. За потреби нейтральних рівнів використовуються наявні `background`, `text`, `divider`, `secondary` або погоджені нові нейтральні токени без зміни фірмових кольорів.

Ручне перемикання світлої, темної та системної схеми зберігається через MUI з `cssVariables.colorSchemeSelector: 'data'`.

### 5.2 Каркас

| Елемент              | Вимога                                                                                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Бічна панель desktop | Зафіксована ліворуч, ширина `280px`, видима від `lg`; логотип/назва Kedr, список маршрутів, активний стан, наведення та вимкнений стан                                                           |
| Верхня панель        | Липка, висота не менше `56px` (цільовий референс `64px`), кнопка мобільного меню, доступні дії, профіль і перемикач теми                                                                         |
| Вміст                | Зсунутий на ширину бічної панелі від `lg`, `Container maxWidth="xl"`, вертикальний відступ сторінки `64px` або погоджений еквівалент                                                             |
| Мобільна навігація   | Тимчасовий `Drawer`, ширина до `320px`, ідентичні desktop-навігація й активний стан, закриття за Escape, натисканням backdrop і вибором внутрішнього пункту                                      |
| Профіль              | Кнопка-аватар з `aria-label`; popover містить ім'я та телефон лише за наявності даних сесії, перехід до account і дію logout                                                                     |
| Breadcrumbs          | В `AdminLayout` відображаються на кожній захищеній сторінці, крім кореневого dashboard, автоматично будуються з поточного маршруту й централізованої мапи назв; останній елемент не є посиланням |

Нижні промоблоки бічної та мобільної навігації із шаблону не входять у межі роботи.

### 5.3 Візуальні компоненти

| Компонент           | Мінімальний контракт                                                                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Картка статистики   | Заголовок, значення, іконка, необов'язковий тренд; не містить запитів даних                                                                              |
| Таблиця             | Контейнер `Card`, горизонтальна прокрутка, шапка, наведення на рядки, порожній стан, завантаження й помилка; пагінація лише за наявності контракту даних |
| Панель інструментів | Заголовок сторінки, breadcrumbs, основні й другорядні дії; на малій ширині дії переносяться без втрати доступу з клавіатури                              |
| Профіль             | Відображає дані поточного користувача, не зберігає токени й не викликає HTTP напряму                                                                     |
| Breadcrumbs         | Централізована мапа надає типізовані сегменти `{ label, to? }` для відомих маршрутів; резервна логіка формує читабельну назву для нового сегмента URL    |

### Фаза 0 — фіксація референсу

1. Зняти скриншоти поточних світлих/темних екранів і референсних екранів шаблону.
2. Зафіксувати список MUI-перевизначень, що переносяться, і список виключених елементів.
3. Уточнити реальні маршрути й наявність API для auth, customers, orders і account.

**Приймання:** є погоджений список екранів, порядок фаз і відсутність спірних фірмових кольорів.

### Фаза 1 — основа теми

1. Додати точки переходу, типографіку, тіні, форму й застосовні перевизначення компонентів до `admin-theme.ts`.
2. Зберегти всі поточні значення палітри у світлій і темній схемах.
3. Перевірити контраст тексту, фокус і вимкнені стани в обох схемах.

**Приймання:** фірмовий зелений і семантична палітра не змінилися; `System`, `Light`, `Dark` працюють і зберігаються; картки, кнопки й таблиці мають погоджені радіус і висоту.

### Фаза 1a — структура теми

1. Розділити тему на логічні модулі: палітра, типографіка, тіні та перевизначення компонентів.
2. Зберегти публічний імпорт теми й поведінку всіх колірних схем.

**Приймання:** структура теми відповідає архітектурним межам, а світла, темна й системна схеми працюють без регресій.

### Фаза 2 — shell і навігація

1. Розділити поточний `AdminLayout` на невеликі компоненти всередині `admin/core/shell` без зміни публічного API компонування.
2. Додати бічну панель, липку верхню панель і адаптивний мобільний drawer.
3. Під'єднати навігаційну конфігурацію лише до наявних маршрутів.
4. Додати popover профілю, використовуючи `logout` з `@admin/core/auth`; дані профілю показувати лише із затвердженого джерела.

**Приймання:** навігація desktop і mobile доступна з клавіатури, активний маршрут підсвічений, logout очищає сесію, поточні маршрути не ламаються.

### Фаза 3 — спільні візуальні примітиви

1. Реалізувати панель інструментів, breadcrumbs і картку статистики в найменшій придатній доменній бібліотеці.
2. Реалізувати оболонку таблиці з типізованими props і обов'язковими станами даних.
3. Застосувати компоненти на вже наявних сторінках без підміни бізнес-даних.

**Приймання:** код компонування не дублюється на сторінках; усі інтерактивні елементи та елементи лише з іконками мають доступні назви.

### Фаза 4 — dashboard

**Статус:** виконано 2026-07-23.

1. Замінити чернетковий `DashboardPage` композицією dashboard зі статистичних карток і затверджених блоків.
2. Для відсутніх метрик показувати інформативний порожній стан, а не числа із шаблону.
3. Під'єднати реальні дані лише через доменний шар data-access.

**Приймання:** dashboard візуально відповідає референсу, не містить текстів Devias і фіктивних бізнес-показників.

### Фаза 5 — customers і orders

1. Створити функціональність лише після затвердження контракту списку клієнтів і прав доступу.
2. Реалізувати панель фільтрів, таблицю, вибір і серверну пагінацію відповідно до API.
3. Додати URL-параметри фільтра/сторінки, якщо це погоджено з продуктом.
4. Створити окрему функціональність orders лише після затвердження контракту списку замовлень і прав доступу.

**Приймання:** пошук, вибір і пагінація не втрачають стан непередбачувано; порожня вибірка, завантаження й помилка помітно відрізняються для customers і orders.

### Фаза 6 — auth і account менеджера

1. Створити публічні сторінки `/login` і `/register` після затвердження auth-контрактів і правил реєстрації.
2. Створити `/account` для імені й номера телефону поточного менеджера після затвердження контракту профілю.
3. Форми реалізувати через наявний підхід Admin; повідомлення про помилки спрямовувати через поточний провайдер сповіщень.

**Приймання:** форма не надсилається двічі, помилки доступні програмі зчитування з екрана, секрети й токени не виводяться в UI або логи; профіль менеджера не показує вигаданих даних.

## 7. Сценарії

1. **Навігація desktop.** Користувач на широкому екрані вибирає пункт бічної панелі й бачить відповідну сторінку з активним пунктом і breadcrumbs.
2. **Навігація mobile.** Користувач відкриває меню й вибирає внутрішній маршрут; drawer закривається, фокус не залишається на прихованому елементі.
3. **Зміна теми.** Користувач вибирає режим у верхній панелі; кольори бренду залишаються поточними, а вибір зберігається після оновлення сторінки.
4. **Профіль.** Користувач відкриває popover аватара, переходить до account або завершує сеанс. За відсутності профілю інтерфейс не показує вигадані ім'я чи телефон.
5. **Табличні дані.** Користувач бачить завантаження, порожній стан, помилку або стан із даними й може користуватися таблицею без порушення горизонтального компонування на mobile.

## 8. Перевірка для кожної фази

- Запустити точкові тести змінених бібліотек і додати тести лише для нової інтерактивної логіки.
- Виконати `npx nx lint admin` і lint затронутих бібліотек.
- Виконати `npx nx build admin`.
- Ручна перевірка: `320px`, `768px`, `1200px`; світла/темна/системна схема; навігація з клавіатури; видимий фокус; відсутні дані, завантаження й помилка.
- Порівняти екран із шаблоном за структурою, відступами, радіусом, висотою й типографікою, але не за палітрою.

## 9. Ризики та відкриті рішення

- В `auth-session.ts` поки немає публічного контракту поточного користувача; до його появи UI профілю повинен бути нейтральним або приховувати персональні поля.
- Для auth, customers, orders і account не знайдено затверджених контрактів API. Їхня реалізація починається після окремої SDD-специфікації домену.
- Точний склад нейтральної шкали для складних станів потрібно погодити, якщо поточних `background/text/divider/secondary` недостатньо.
- Шаблон використовує Next.js і сторонній набір іконок; переносити потрібно поведінку й візуальні правила, а не вихідний код.
